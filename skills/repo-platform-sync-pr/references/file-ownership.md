# File classes and the decision rule per class

<!-- Keep in sync with the twin copy in skills/repo-platform-new-project/
     references/file-ownership.md - skills install standalone, so the table is duplicated. -->

Classify every file a sync PR touches before deciding what to do with a conflict or a surprising diff.

| Class | Files | Decision rule in a sync PR |
|---|---|---|
| Fully managed (template-owned) | `.github/.copier-answers.yml` (one sanctioned edit; see notes), `.github/repo-platform-manifest.json` (the machine-readable ownership map; see notes), `.github/workflows/ci.yml`, `release.yml` (the release pipeline: draft cut, repo-owned update hook, attested publish), `dependabot-bun-lockfile.yml` (bun module), `validate-skills.yml` (skills module), thin workflow callers (`auto-assign.yml`, `pages.yml`, `docs-site.yml`, `settings-sync.yml`), `dependabot.yml`, toolchain pin dotfiles (`.bun-version`, `.node-version`, `.dvmrc`), `CODE_OF_CONDUCT.md`, `.yamllint`, `.typography-allow`, agent-file symlinks | Accept the template side. Overlapping local edits lose to the template (a non-overlapping edit can survive a given sync, but it is unowned); move the need into a repo-owned file or into the template itself |
| Managed shape, repo-owned selection | `.repo-platform.yml` | The `modules:` list is the repo's own; the file's shape is managed |
| Split (managed region) | `SECURITY.md`, `CONTRIBUTING.md` (public repos only), `LICENSE.md`, `AGENTS.md`, `.gitattributes`, `.editorconfig`, `.github/CODEOWNERS`, `.gitignore` | Everything OUTSIDE the `BEGIN/END REPO-PLATFORM MANAGED` marker pair - above BEGIN and below END - is repo-owned; the bounded region between them is managed. The semantics favor the repo's half where it matters: .editorconfig applies later sections over earlier ones, CODEOWNERS applies the LAST matching pattern, and .gitignore is last-match-wins, so entries below the END marker override the managed region. Sync REBUILDS these files structurally on every run: the managed region comes from a clean render, both repo-owned sides ride through byte-for-byte, and edits INSIDE the region are reset (flagged as "managed-region edits reset" in the PR body's carry summary; the PR stays manual-review). A repo still in a RETIRED split shape (the old `repo-platform:local-section` tail marker, or the old `.gitignore` LOCAL region) is NOT converted - that one-time machinery is deleted: the sync refuses the old-vintage manifest loudly, and the previous copy is preserved in full below the END marker under a recovery-appendix comment with `recover=recopy` named as the fix - reconcile manually. A previous copy that splits at no known shape takes the same recovery appendix. A deletion-dominant diff on one of these still means repo-owned content loss - restore before merging |
| Generated once, then repo-owned (`_skip_if_exists`) | `.github/workflows/checks.yml`, `update-release.yml` (the update hook `release.yml` calls between draft and publish), `update-release-pr.yml` (the hook `release.yml` calls when release-please creates or refreshes the release PR), `auto-format.yml`, `copilot-setup-steps.yml`, `nightly-fuzz.yml`, `nightly.yml`, issue forms and chooser config, `release-please-config.json`, `.release-please-manifest.json`, `.gitleaks.toml`, `.github/actionlint.yaml`, `.claude-plugin/plugin.json` and `marketplace.json` (skills module), `.github/settings.yml` (settings-sync module; never deleted by sync - identity keys + local overrides, merged OVER the centrally computed fleet and module layers at apply time, and UNDER the fleet override layer) | Never touched once they exist. A first-time ADDITION is expected when the same PR's `.repo-platform.yml` diff adds the owning module; a MODIFICATION or DELETION is suspicious - stop and investigate. One sanctioned exception: the one-time settings.yml layering transition (see notes) |
| Repo-owned (never touched) | source code, release tooling, `.typography-allow.local`, everything else | The template never renders these paths; they appear only in the retired-file deletion list, and then only if the path was once template-rendered |

Notes:

- `.github/.copier-answers.yml` is managed; the one sanctioned edit is changing a question's VALUE key via a default-branch PR to set a module parameter (`nightly_label`, `skills_dir`, `pages_*`, `fuzzer_label`, ...) - the sync loads those values from the recorded answers, so the edit sticks. Never touch the underscore keys (`_commit`, `_src_path`).
- A `.bun-version`, `.node-version`, or `.dvmrc` addition or version bump in a sync PR is expected: toolchain pins are fleet-wide managed files (one shared version per toolchain, advanced by repo-platform's refresh-toolchains workflow). Deliberate divergence belongs in the repo-owned workflows' version inputs, not in the dotfile - a hand-edited copy is overwritten on the next sync.
- `.github/repo-platform-manifest.json` maps every template-landed path to its ownership class and records a content hash per managed file (the manifest's own entry deliberately stays null - a self-hash would be circular), stamped at render time. Hash-and-ref churn in a sync PR is expected, not suspicious. Never hand-edit it: sync restamps hashes and provenance but does NOT heal edited class metadata (a normal update can even baseline a non-conflicting manifest edit). The validator's roster cross-check catches a tampered class on roster-covered paths (the managed and split files the template version pins); starters, toolchain pins, and symlinks are manifest-trusted, so an edit there is caught only by this review pass. Fix a tampered manifest by reverting the edit or a recovery recopy, not by waiting for the next sync.
- `LICENSE.md` carries the fleet license; with the `custom-license` module it is the repo's own license and sync never touches it. An update that DELETES a license file is flagged in the PR body: content below its marker does not survive a delete-vs-modify merge, so check the old file for local notices worth moving.
- `CONTRIBUTING.md` is a public-only render: a repo flipped private has it retired, local section included.
- `.github/settings.yml` is a repo-owned starter: it carries the repo's identity keys and local overrides, and repo-platform merges the fleet and module settings layers centrally at apply time and layers this file OVER them - then the fleet override layer over that, so the invariants it declares (squash-only merging, the branch protection rulesets) cannot be beaten from here. One sync REPLACES a legacy full-baseline copy (the one still carrying the retired `# repo-platform:mergeable` marker) with the identity starter; that PR stays manual-review and lists the dropped non-baseline declarations - re-add wanted overrides to the new file before merging.
- The authoritative generated-once list is `_skip_if_exists` in repo-platform's `copier.yml`.
