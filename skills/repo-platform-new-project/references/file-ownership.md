# File ownership in a managed repository

<!-- The Class and Files columns are one roster with skills/repo-platform-sync-pr/references/file-ownership.md (skills install standalone, so each ships its own table); repo-platform's check_ssot skill-ownership-tables rule fails on any difference between the two. The third column is this skill's own. -->

Who owns what after generation. "Managed" files are template-owned; "repo-owned" files are yours.

| Class | Files | What that means |
|---|---|---|
| Fully managed (template-owned) | `.github/.copier-answers.yml` (one sanctioned edit; see notes), `.github/repo-platform-manifest.json` (the machine-readable ownership map; see notes), `.github/workflows/ci.yml` (one byte-identical skeleton for the whole fleet), `dependabot-bun-lockfile.yml` (bun module), `validate-skills.yml` (skills module), thin workflow callers (`auto-assign.yml`, `pages.yml`, `docs-site.yml`), `dependabot.yml`, toolchain pin dotfiles (`.bun-version`, `.node-version`, `.dvmrc`), `.github/CODE_OF_CONDUCT.md`, `.yamllint`, `.typography-allow`, agent-file symlinks, `.github/instructions/review.instructions.md` (base content: Copilot code review wording rules) | Do not edit; local edits that overlap a template change lose to the template on sync (with review), and even non-overlapping edits are unowned |
| Managed shape, repo-owned selection | `.repo-platform.yml` | Its presence enrolls the repo; its top-level `modules:` list is yours - edit it and the next sync applies the change |
| Split (managed region) | `.github/SECURITY.md`, `CONTRIBUTING.md` (public repos only), `LICENSE.md`, `AGENTS.md`, `.gitattributes`, `.editorconfig`, `.github/CODEOWNERS`, `.gitignore` | Everything OUTSIDE the `BEGIN/END REPO-PLATFORM MANAGED` marker pair - above BEGIN and below END - is yours; the bounded region between them is managed. The semantics favor your half where it matters: .editorconfig applies later sections over earlier ones, CODEOWNERS applies the LAST matching pattern, and .gitignore is last-match-wins, so entries below the END marker override the managed region. Sync rebuilds these files structurally on every run: both of your sides ride through byte-for-byte, and edits INSIDE the region are reset (the sync PR flags each reset and stays manual-review) |
| Generated once, then repo-owned (`_skip_if_exists`) | `.github/workflows/checks.yml`, `post-green.yml` (the hook ci.yml calls after the all-green gate on a push to main, before the release), `update-release.yml` (the update hook ci.yml's release leg calls between draft and publish), `update-release-pr.yml` (the hook ci.yml calls when release-please creates or refreshes the release PR); both seeded in every repository, `auto-format.yml`, `copilot-setup-steps.yml`, `nightly-fuzz.yml`, `nightly.yml`, issue forms and chooser config, `release-please-config.json`, `.release-please-manifest.json`, `.gitleaks.toml`, `.github/actionlint.yaml`, `.claude-plugin/plugin.json` and `marketplace.json` (skills module), `.github/settings.yml` (never deleted by sync - identity keys + local overrides, merged OVER the centrally computed fleet and module layers at apply time, and UNDER the fleet override layer) | Seeded on first render (adding a module later seeds its starters in that sync PR, and a new base starter arrives in the sync PR that introduces it), then never overwritten - fill them in freely |
| Repo-owned (never touched) | source code, release tooling, `.typography-allow.local`, everything else | The template never renders these paths |

Notes:

- `.github/.copier-answers.yml` is managed; the one sanctioned edit is changing a question's VALUE key via a default-branch PR to set a module parameter (`nightly_label`, `skills_dir`, `pages_*`, `fuzzer_label`, ...) - the sync loads those values from the recorded answers, so the edit sticks. Never touch the underscore keys (`_commit`, `_src_path`).
- The toolchain pin dotfiles (`.bun-version`, `.node-version`, `.dvmrc`) are fleet-wide: sync PRs add and bump them (one shared version per toolchain). Override a version in your repo-owned workflows' version inputs, not by editing the dotfile.
- `.github/repo-platform-manifest.json` is the machine-readable version of this table: every template-landed path with its ownership class, plus a content hash per managed file (the manifest's own entry stays null - a self-hash would be circular), stamped at render time. Sync restamps the hashes and template ref whenever the render changes; never hand-edit it - edited class metadata is not healed by a normal sync, and the validator's cross-check covers every roster path (managed, split, and class-only pins and symlinks), not starters. The `validate-template` job blocks on managed files that changed since the sync last stamped them, on a listed managed file that is missing, and on a roster path the manifest does not list.
- `LICENSE.md` carries the fleet license (Individual and Small Organization License); local notices (third-party components) go below its marker. With the `custom-license` module the file is the repo's own license and sync never touches it.
- `CLAUDE.md`, `.github/copilot-instructions.md`, and `.github/agents.md` are symlinks to `AGENTS.md` (base content of every render): one source of truth.
- `.github/settings.yml` is yours: identity keys + local overrides, never deleted by sync. The fleet and module layers are computed centrally and merged UNDER it at apply time; one layer sits ABOVE it - `.github/settings-override.yml` in repo-platform, the fleet invariants - so your file cannot beat what that layer declares.
- The authoritative generated-once list is `_skip_if_exists` in repo-platform's `copier.yml`.
