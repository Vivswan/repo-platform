# The fleet docs theme

This directory is the ONE home of the fleet's docs-site look: every managed repository's docs site builds with these files, and none of them exists in any fleet repository (fleet repos carry only markdown). Changes here ship on the next `build` branch publish, and every site picks them up on its next deploy (each site's nightly rebuild makes that automatic - no per-repo work).

The base skin is [vitepress-carbon](https://github.com/brenoepics/vitepress-carbon) (GitHub-monochrome, token-based), pinned exact in `../../package.json` next to the exact `vitepress` pin - both bumped only by deliberate commits here, never by a floating range.

## The customization contract

| File | What it controls | Changing it |
|---|---|---|
| `custom.css` | The fleet TOKEN LAYER: carbon's `--vp-*` custom properties set to the fleet's values (grounds, text tiers, dividers, code, custom blocks, buttons, nav and sidebar metrics) for `:root` (light) and `.dark`, the self-hosted font stacks, and the six per-repository hues under `html[data-fleet-hue="N"]` / `html.dark[data-fleet-hue="N"]` | Carbon's design system is `--vp-*` custom properties (the authoritative token list is `packages/theme/src/theme/styles/vars.css` in carbon's repo), so a palette change is a set of values here - never edit carbon. Everything that carries color reads `--fleet-hue`: add a hue by adding a pair of blocks, never by writing a hex elsewhere. |
| `components.css` | Component rules over carbon (nav bar, sidebar, outline, prose, tables, code, custom blocks, pager), the version select, the facts card, the provenance line, and the landing-page aside layout | Selectors are prefixed with carbon's block classes to outrank its scoped styles. Reading rules hold: running prose at line-height 1.65 or more (compact rows in tables, the facts card and the provenance line sit between 1.45 and 1.6), left-aligned, emphasis by weight (never italics), sentence-case labels, the hue as the only accent. |
| `index.ts` | The theme entry: carbon as base, the font imports, which components mount where, the global `FleetLauncher` registration | Keep exporting a VitePress `Theme`. If you change the `Layout`, keep the four mounts: `NavLauncher` in `nav-bar-content-before`, `VersionSwitcher` in `nav-bar-content-menu-after` (so the DOM and tab order match the visual order: search, version, language, appearance), `FactsPanel` in `aside-top`, `Provenance` in `doc-after` (carbon forwards all default-theme slots). `enhanceApp` must keep `ctx.app.component("FleetLauncher", ...)`: the landing-table rule emits that tag, and an unregistered tag renders empty. The fonts are `@fontsource-variable` packages imported before the CSS (self-hosted; remote font links are banned, and `../config.mts`'s PostCSS filter drops carbon's own remote `@import` rules). |
| `version-switcher.ts` | The version dropdown (class `docs-site-version-switcher`) | Restyle or replace freely, but keep reading `themeConfig.docsSiteVersions` and `docsSiteCurrent` - that is the build-time contract with the pages-site action, and versioned sites lose version navigation without it. |
| `facts-panel.ts` | The project facts card (class `fleet-facts`) on landing pages: name, description, repository, homepage, topics, toolchain versions, served versions, license | Renders only when `frontmatter.fleetLanding` and `themeConfig.docsSiteFacts` both exist. The card's grammar is hairline rows with section heads by weight, values right-aligned, the hue only on the title rule and the repository link. |
| `provenance.ts` | The provenance line (class `fleet-provenance`) under every page: the ref and commit the tier was built from, and the page's source file | Reads `themeConfig.docsSiteFacts` (its `provenance` and `docsDir`) and `page.filePath`, so the source reads as a repository path (`docs/guide/README.md`); renders nothing without facts. |
| `pages.data.ts` | The launcher's page-and-heading index, built once per site build from the docs tree (URL, title, directory, locale, h2/h3 anchors per page) | Keep exporting `data: PageIndexEntry[]`; the launcher component reads it. It renders every page through the shared renderer, so it needs `headersRule` and `inlineTextRule` installed by `../config.mts`. A page that uses a VitePress `@include` directive lists no heading rows: the directive expands only in the page transform, so the unexpanded source would shift or collide its anchors. Full-text search still reaches those headings. |
| `launcher.ts` | The search launcher component, registered globally as `FleetLauncher` (class `fleet-launcher`): the field with the shortcut keycaps, the grouped list with fold rows and the roving highlight, Enter/Escape handling, and the full-text fallback (a "Text matches" group from VitePress's local search index when no page or heading matches) | Mounted from the `<FleetLauncher rows="...">` tag the landing-table rule emits (mode `panel`) and by `nav-launcher.ts` (mode `dialog`). The list renders server-side from `rows` and `pages.data.ts`; keep browser APIs inside `onMounted` and handlers. Pure helpers (fold rows, key tests, the highlight) live in `launcher-view.ts` (tested without a VitePress process); grouping and matching rules stay in `launcher-model.ts`. |
| `nav-launcher.ts` | The nav's launcher entry (class `fleet-launcher-button`), opening the launcher in a native `<dialog>` (class `fleet-launcher-dialog`), and the shortcut owner: Cmd K, Ctrl K, and `/` outside a field focus the landing panel when the page has one, else open the dialog | Mounted in `nav-bar-content-before` on every page; `launcher.css` hides the button while a landing panel is on the page, so a landing page without a curated table still has search. The shortcut is a capturing window listener that stops carbon's own search hotkeys; keep it, or carbon's hidden search box opens instead. |
| `launcher.css` | The launcher's rules: panel material, the 64px field, group heads and rows, the fold row, the empty state, the nav button, the dialog, the mobile collapse, and `.VPNavBar .VPNavBarSearch { display: none }` (carbon's search button retired; `search: local` stays in `../config.mts` so the index the fallback loads still ships) | The hue appears on the highlighted row, the focused field, and focus rings only; matches are bold, never colored. Rows that can wrap (labels, notes, group heads, the fold button, the empty state) sit at line-height 1.6; the single-line controls (the input, the keycaps, the nav button) sit at 1.5. Keep `prefers-reduced-motion` honored. |
| `local-search.d.ts` | The ambient type for VitePress's `@localSearchIndex` virtual module (one lazy loader per locale key, resolving to the serialized MiniSearch index) | Type-only and hand-written to the shape VitePress's local-search plugin emits today; tsc trusts it, so a VitePress bump must be checked against the plugin's `load()` output by hand. |
| `launcher-model.ts` | The launcher's pure model: curated rows plus the page index become filterable groups (`buildGroups`, `filterGroups`, `matchRanges`) | Browser-safe by construction: no node imports, because the client bundle imports it. Change the grouping, folding (8 items), or matching rules here, never in the component. |
| `../landing-table.ts`, `../inline-text.ts` | The landing-page markdown rule: the first table with a column of bare links on a locale root's index.md becomes `<FleetLauncher rows="...">`; inline-text.ts stamps plain text on every inline token for it and for the page index | `../config.mts`'s `markdown.config` installs FOUR rules: these two, `headersRule` from `page-index.ts`, and `alertTitlesRule` from `../custom-blocks.ts` (GitHub-style alert titles); keep all four there or the readers throw. A table without a link column, or on any other page, renders as a table. |
| `../config.mts` | Site structure: carbon's `baseConfig`, title/base/srcDir wiring (env-driven, leave intact), sidebar and rewrites (from `derive.ts`), locales, search, editLink, the PostCSS filter that drops remote `@import` rules (carbon's Google Fonts and cdnfonts links), and the facts contract: `DOCS_SITE_FACTS` (JSON `ProjectFacts` from `../../facts.ts`) into `themeConfig.docsSiteFacts`, `frontmatter.fleetLanding` (with `outline: false`) on landing pages, `data-fleet-hue` on `<html>` | Adjust `themeConfig` freely; the `DOCS_SITE_*` env contract at the top of the file belongs to the action and must keep working. |
| `../derive.ts` | Sidebar, route, and locale derivation from the docs tree | Change the derivation rules here to change every site's navigation shape. |
| `../table-wrap.ts` | The markdown-it rule that wraps every top-level table in `div.vp-table`, the scroll fallback `components.css` styles (a table wider than the doc column scrolls inside the wrapper; narrow ones still span it) | Registered from `../config.mts` as `markdown.preConfig`. Nested tables (blockquotes, lists) stay bare. |

## The VitePress 2 path (deferred deliberately)

`vitepress` stays on the 1.6 line because carbon tracks it (carbon@1.6.0 declares no VitePress 2 compatibility). When VitePress 2 goes stable, either carbon has ported (bump both pins together) or the move is a token port: reimplement carbon's `vars.css` values over VitePress's default theme in this directory - the file layout and the contract table above are built so that swap stays local to this directory plus `../config.mts`'s `extends`/theme imports.

## Content rules

- Fleet docs are plain `.md` only - no MDX and no per-repo Vue components. Rich widgets are added HERE, as theme-provided [markdown containers](https://vitepress.dev/guide/markdown#custom-containers) or globally registered components, so every repository gets them for free.
- Translations follow one convention: `docs/<lang>[-<region>]/` (a two-letter ISO 639-1 code, e.g. `zh-cn/`, `ja/`) mirroring the root structure. Detected directories become VitePress locales with the language switcher in the nav (carbon ships the translations menu); the root tree is the default (English) locale. The detection rule lives in `../derive.ts`.
- The dropdown navigates to a version's ROOT, not the same page in the other version - page sets differ across versions, so deep cross-version links are not guaranteed to exist.
