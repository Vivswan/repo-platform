# The fleet docs theme

This directory is the ONE home of the fleet's docs-site look: every managed repository's docs site builds with these files, and none of them exists in any fleet repository (fleet repos carry only markdown). Changes here ship on the next `build` branch publish, and every site picks them up on its next deploy (each site's nightly rebuild makes that automatic - no per-repo work).

The base skin is [vitepress-carbon](https://github.com/brenoepics/vitepress-carbon) (GitHub-monochrome, token-based), pinned exact in `../../package.json` next to the exact `vitepress` pin - both bumped only by deliberate commits here, never by a floating range.

## The customization contract

| File | What it controls | Changing it |
|---|---|---|
| `custom.css` | The fleet TOKEN LAYER: carbon's `--vp-*` custom properties set to the fleet's values (grounds, text tiers, dividers, code, custom blocks, buttons, nav and sidebar metrics) for `:root` (light) and `.dark` (the sidebar token narrows from 320px to 280px between 768px and carbon's 1280px aside breakpoint, where the sidebar shares the width with the article alone; `--fleet-gutter` is the margin each side of the 1440px frame on a wider viewport, 0 below it, and every rule that offsets something into the frame reads it), the self-hosted font stacks, and the six per-repository hues under `html[data-fleet-hue="N"]` / `html.dark[data-fleet-hue="N"]` | Carbon's design system is `--vp-*` custom properties (the authoritative token list is `packages/theme/src/theme/styles/vars.css` in carbon's repo), so a palette change is a set of values here - never edit carbon. Everything that carries color reads `--fleet-hue`: add a hue by adding a pair of blocks, never by writing a hex elsewhere. |
| `components.css` | Component rules over carbon (nav bar, sidebar, outline, prose, tables, code, custom blocks, pager), the version select, the facts card, the provenance line, and the landing-page aside layout (below carbon's 1280px aside breakpoint the facts card sits in flow ABOVE the article, the way a repository's About card leads its README on a phone) | Selectors are prefixed with carbon's block classes to outrank its scoped styles. The sidebar's width is the `--vp-sidebar-width` token: the rules here lift carbon's 230px drawer cap so the desktop sidebar is the token and the mobile drawer is `min(100vw - 64px, token)`, and let the group take the nav's inner width, so widen the token, never a rule here; nested lists indent only under a visible group head, with no rule down their edge; on a viewport wider than the frame the sidebar, the nav's title and controls sit on the frame's edges (the same `--fleet-gutter` carbon offsets the article by), so the list stays next to the article. The nav shows the appearance switch inline from 768px (carbon parks it in the "..." flyout until 1280px) and hides that flyout when nothing else would be in it; between 768px and 1279px a site with locales therefore shows the switch before the language flyout, since carbon keeps translations in that flyout there. The row above the article (breadcrumb, Markdown menu, Edit link) is one height, `--fleet-content-top-height` on `.VPDoc`, that the aside's top and the landing card's top read to sit level with the h1; its two controls are 32px icon buttons whose labels stay in the DOM as their accessible names. Reading rules hold: running prose at line-height 1.65 or more (compact rows in tables, the facts card and the provenance line sit between 1.45 and 1.6), left-aligned, emphasis by weight (never italics), sentence-case labels, the hue as the only accent. |
| `index.ts` | The theme entry: carbon as base, the font imports, which components mount where, the global `FleetLauncher` registration | Keep exporting a VitePress `Theme`. If you change the `Layout`, keep the four mounts: `NavLauncher` in `nav-bar-content-before`, `VersionSwitcher` in `nav-bar-content-menu-after` (so the DOM and tab order match the visual order: search, version, language, appearance), `FactsPanel` in `aside-top`, `Provenance` in `doc-after` (carbon forwards all default-theme slots). `enhanceApp` must keep `ctx.app.component("FleetLauncher", ...)`: the landing-table rule emits that tag, and an unregistered tag renders empty. In the browser `enhanceApp` also stamps `data-fleet-hue` on `<html>` from `themeConfig.docsSiteFacts` when the attribute is missing: built pages carry it from `../config.mts`'s `transformHtml` (so there is no flash), and `vitepress dev`, which never runs that hook, gets it here. The fonts are `@fontsource-variable` packages imported before the CSS (self-hosted; remote font links are banned, and `../config.mts`'s PostCSS filter drops carbon's own remote `@import` rules). |
| `version-switcher.ts` | The version dropdown (class `docs-site-version-switcher`) | Restyle or replace freely, but keep reading `themeConfig.docsSiteVersions` and `docsSiteCurrent` - that is the build-time contract with the pages-site action, and versioned sites lose version navigation without it. |
| `facts-panel.ts` | The project facts card (class `fleet-facts`) on landing pages: name, description, repository, homepage, topics, toolchain versions, served versions, license | Renders only when `frontmatter.fleetLanding` and `themeConfig.docsSiteFacts` both exist. The card is one grid: every section (a `dl`), row, and nested item list is a subgrid of it, so the label column is shared and values start on one line; a counted group (toolchains, versions) keeps its items INSIDE its value cell (`fleet-facts-items`), which is what lets `components.css` lay the same markup out two ways: indented rows under the count in the aside (1280px and up), and, in flow above the article, a compact strip with left-aligned values, the items inline after their label, the count hidden, and the description clamped to two lines. Section heads by weight, the hue only on the title rule and the repository link; topics are chips (`fleet-facts-topic`) under their label at the card's full width, each wrapping whole. The card is an `aside` labelled by its title (`aria-labelledby`), and the title is a `p`, never a heading: the aside-top slot renders before the page h1, and a heading there would break the heading order. Path-like values (repository, homepage) render one inline-block segment per slash (class `fleet-facts-segment`, a `<wbr>` between) so a wide value splits at a slash first; a segment wider than the column alone falls back to `overflow-wrap: anywhere`. |
| `provenance.ts` | The provenance line (class `fleet-provenance`) under every page: the ref and commit the tier was built from, and the page's source file | Reads `themeConfig.docsSiteFacts` (its `provenance` and `docsDir`) and `page.filePath`, so the source reads as a repository path (`docs/guide/README.md`); renders nothing without facts. It is a `section` with `aria-label="Page provenance"`, a region landmark of its own, so the line never falls outside every landmark; never a `footer`, since carbon's doc footer, when present, already supplies the page's contentinfo landmark. |
| `pages.data.ts` | The launcher's page-and-heading index, built once per site build from the docs tree (URL, title, directory, locale, h2/h3 anchors per page) | Keep exporting `data: PageIndexEntry[]`; the launcher component reads it. It renders every page through the shared renderer, so it needs `headersRule` and `inlineTextRule` installed by `../config.mts`. A page with a VitePress `@include` directive that VitePress would expand lists no heading rows: the directive expands only in the page transform, so the unexpanded source would shift or collide its anchors. Full-text search still reaches those headings. The test mirrors VitePress's own resolution (relative to the page, `@/` against srcDir, region and range suffixes stripped) and asks whether that path is a regular file, so a directive VitePress cannot read (a missing file, a directory, a path through a file), the usual case for one quoted in prose or a code span, changes nothing. |
| `launcher.ts` | The search launcher component, registered globally as `FleetLauncher` (class `fleet-launcher`): the combobox field with the shortcut keycaps, the grouped listbox with fold rows and the roving highlight, Enter/Escape handling, and the full-text fallback (a "Text matches" group from VitePress's local search index when no page or heading matches) | Mounted from the `<FleetLauncher rows="...">` tag the landing-table rule emits (mode `panel`) and by `nav-launcher.ts` (mode `dialog`). The list renders server-side from `rows` and `pages.data.ts`; keep browser APIs inside `onMounted` and handlers. The ARIA shape is the combobox-listbox pattern and must stay one: the field (`role=combobox`, `aria-expanded` false over an empty list) points at the highlighted option through `aria-activedescendant`; each group is a `div[role=group]` labelled by its title and carrying `aria-expanded` when it folds; every option is the interactive element itself (the row link with `tabindex=-1`, or the fold row `div`, whose Show/Hide label states the fold), so nothing inside the list is in the Tab order and Enter clicks the highlighted option. The section carries `data-keyboard` while the reader's last input was a key (the exported `keyboardInput` ref, written by `nav-launcher.ts`); `launcher.css` shows the field's focus ring on that flag, never on `:focus-visible` alone, which Chromium matches for programmatic focus too. Pure helpers (the option list with its fold rows, key tests, the highlight) live in `launcher-view.ts` (tested without a VitePress process); grouping and matching rules stay in `launcher-model.ts`. |
| `nav-launcher.ts` | The nav's launcher entry (class `fleet-launcher-button`), opening the launcher in a native `<dialog>` (class `fleet-launcher-dialog`) with a Close button (class `fleet-launcher-close`, `aria-label="Close search"`, after the launcher in the DOM so Tab from the field reaches it), and the shortcut owner: Cmd K, Ctrl K, and `/` outside a field focus the landing panel when the page has one, else open the dialog | Mounted in `nav-bar-content-before` on every page; `launcher.css` hides the button while a landing panel is on the page, so a landing page without a curated table still has search. The shortcut is a capturing window listener that stops carbon's own search hotkeys; keep it, or carbon's hidden search box opens instead. The same listener (with a pointerdown twin) writes `launcher.ts`'s `keyboardInput` ref, so the key that opens the dialog counts as keyboard input for the field's focus ring even though the launcher mounts after it. |
| `launcher.css` | The launcher's rules: panel material, the 64px field, group heads and rows, the fold row, the empty state, the nav button (from 960px to 1279px positioned against the full-width nav bar and centered on the viewport, its width backing off from the title column; from 1280px up, on pages with a sidebar, back in the nav's flex row with its left edge on the article's left edge and its width the article's, by carbon's own arithmetic restated, shrinking when the nav's controls need the room rather than overlapping them (a page without a sidebar, the 404, stays centered; a page without an aside follows the article's centered column); from 768px to 959px it sits in the nav's flex row centered; below 768px it is a 48px icon docked beside the hamburger, and its hover border is behind `(hover: hover)` so a tap does not leave it lit), the dialog, the mobile collapse, and `.VPNavBar .VPNavBarSearch { display: none }` (carbon's search button retired; `search: local` stays in `../config.mts` so the index the fallback loads still ships) | The hue appears on the highlighted row (the tint plus a 2px inset ring), the focused field (the icon on focus, plus a 2px inset ring on the field wrapper while the launcher carries `data-keyboard`), and focus rings only; each state has a non-color cue at 3:1 or better against the panel, and matches are bold, never colored. Rows that can wrap (labels, notes, group heads, the fold row, the empty state) sit at line-height 1.6; the single-line controls (the input, the keycaps, the nav button) sit at 1.5. Hover-only rules stay under `@media (hover: hover)` so a tap never leaves one stuck on. The dialog is a flex column sized in `dvh` units (the list takes what the field and the status line leave), and the nav button hides while its dialog is open. Keep `prefers-reduced-motion` honored. |
| `local-search.d.ts` | The ambient type for VitePress's `@localSearchIndex` virtual module (one lazy loader per locale key, resolving to the serialized MiniSearch index) | Type-only and hand-written to the shape VitePress's local-search plugin emits today; tsc trusts it, so a VitePress bump must be checked against the plugin's `load()` output by hand. |
| `launcher-model.ts` | The launcher's pure model: curated rows plus the page index become filterable groups (`buildGroups`, `filterGroups`, `matchRanges`); a page row's note is its site path (`guide/setup`), a heading row's the page title | Browser-safe by construction: no node imports, because the client bundle imports it. Change the grouping, folding (a page group folds its headings when it has two or more, keeping its curated and page rows in view; a directory group folds past 8 items; `splitRows` says which rows a fold hides), or matching rules here, never in the component. |
| `../landing-table.ts`, `../inline-text.ts` | The landing-page markdown rule: the first table with a column of bare links on a locale root's index.md becomes `<FleetLauncher rows="...">`; inline-text.ts stamps plain text on every inline token for it and for the page index | `../config.mts`'s `markdown.config` installs FOUR rules: these two, `headersRule` from `page-index.ts`, and `alertTitlesRule` from `../custom-blocks.ts` (GitHub-style alert titles); keep all four there or the readers throw. A table without a link column, or on any other page, renders as a table. |
| `../config.mts` | Site structure: carbon's `baseConfig`, title/base/srcDir wiring (env-driven, leave intact), sidebar and rewrites (from `derive.ts`), locales, search, editLink, the PostCSS filter that drops remote `@import` rules (carbon's Google Fonts and cdnfonts links), and the facts contract: `DOCS_SITE_FACTS` (JSON `ProjectFacts` from `../../facts.ts`) into `themeConfig.docsSiteFacts`, `frontmatter.fleetLanding` (with `outline: false`) on landing pages, `data-fleet-hue` on `<html>` | Adjust `themeConfig` freely; the `DOCS_SITE_*` env contract at the top of the file belongs to the action and must keep working. |
| `../derive.ts` | Sidebar, route, and locale derivation from the docs tree | Change the derivation rules here to change every site's navigation shape. |
| `../table-wrap.ts` | The markdown-it rule that wraps every top-level table in `div.vp-table`, the scroll fallback `components.css` styles (a table wider than the doc column scrolls inside the wrapper; narrow ones still span it) | Registered from `../config.mts` as `markdown.preConfig`. Nested tables (blockquotes, lists) stay bare. |
| `../dir-title.ts` | A directory's display title (`api-reference/` reads as Api Reference), shared by the sidebar groups and the launcher's directory groups | Browser-safe (the client bundle imports it through `launcher-model.ts`); one function so the sidebar and the launcher never name a folder differently. |

## The VitePress 2 path (deferred deliberately)

`vitepress` stays on the 1.6 line because carbon tracks it (carbon@1.6.0 declares no VitePress 2 compatibility). When VitePress 2 goes stable, either carbon has ported (bump both pins together) or the move is a token port: reimplement carbon's `vars.css` values over VitePress's default theme in this directory - the file layout and the contract table above are built so that swap stays local to this directory plus `../config.mts`'s `extends`/theme imports.

## Content rules

- Fleet docs are plain `.md` only - no MDX and no per-repo Vue components. Rich widgets are added HERE, as theme-provided [markdown containers](https://vitepress.dev/guide/markdown#custom-containers) or globally registered components, so every repository gets them for free.
- Translations follow one convention: `docs/<lang>[-<region>]/` (a two-letter ISO 639-1 code, e.g. `zh-cn/`, `ja/`) mirroring the root structure. Detected directories become VitePress locales with the language switcher in the nav (carbon ships the translations menu); the root tree is the default (English) locale. The detection rule lives in `../derive.ts`.
- The dropdown navigates to a version's ROOT, not the same page in the other version - page sets differ across versions, so deep cross-version links are not guaranteed to exist.
